My personal AI workflow, open-sourced

Agentic engineering, with the engineer in the loop.

The workflow I use with Claude Code on most of my projects. The AI plans, builds, and ships. I decide, verify, and understand, without babysitting every keystroke. And it teaches me what it built, so I can maintain the code without it.

Why

The opposite of vibe coding.

Vibe coding is fast until the first change request. The engineer either stops understanding the system or ends up watching every diff, which is slower than writing it. This workflow keeps the speed and puts the engineer where it matters: on decisions, verification, and understanding.

× What vibe coding costs you

  • Code nobody understands. It works today; nobody can explain why, so nobody dares to change it.
  • Changes break things you did not know existed. There is no map of what a feature touches.
  • Tests written after the fact, to pass, or not at all.
  • Decisions made silently. Scope, data model, security behavior: chosen by the agent, noticed later.
  • The spec lives in a chat scroll and is gone by next week.
  • You become the babysitter. Nothing else checks the work, so you read every line, or you stop reading.

✓ What this workflow does instead

  • A plan you approve before any code, with the decisions the agent made listed so you overrule by reading.
  • Tests first, derived from acceptance criteria, then the layers in order with checkpoint commits.
  • A build gate the agent cannot skip: it rebuilds before it stops and blocks on errors.
  • A second agent reviews with fresh eyes for correctness, architecture, data access, security, and scope.
  • One living document per feature: what it does now, its code map, every change and its root cause.
  • An explicit stop-and-ask list (migrations, shared infrastructure, security, scope creep) so you are asked when it matters and not otherwise.
  • Learning modes (auto, pair, coach) and a quiz, so you understand the code without watching it being typed.
Where this sits

One workflow among many. The one I reach for most.

There are many good ways to do agentic engineering. On some projects I let the agents run far ahead; on others I use them very carefully, line by line. This workflow is the middle ground, and it is what I use on roughly two out of three projects. Take it as a working default, not a doctrine.

The dial is yours: quick and deep on planning, auto, pair, and coach on building. The defaults sit in the middle.

The part that matters most

Ship fast, and still understand your own system.

Planning, building, and shipping with an agent is a solved problem; many tools do it. The problem I wanted to solve is what comes after: a codebase I depend on but did not write. So this workflow makes the AI teach me what it implemented, feature by feature, while it is fresh.

If the agents disappeared tomorrow, I should still be able to fix a bug, add a feature, and explain the system on a whiteboard.

walkthrough

After every build. One real request traced through the code, file and line at each hop, the patterns used and why, and a recipe for the next change. Written into the feature's document, not lost in chat.

pair

The AI writes the tests, scaffolding, and wiring. It leaves the one to three core pieces for you, with a hint and an example to copy. The tests already exist, so you know when you are done. Bug fixes in this mode are the fastest way to learn a codebase.

coach

You write it. The AI gives one step at a time, reviews each, and runs the tests. For the parts of the system you do not know yet.

quiz

Five questions, graded honestly. Where does X live, what happens after Y, why this pattern, what breaks if Z changes. Scores go in the feature's document so you know what to revisit.

handbook

Written for a developer without AI. A map of the system, one request traced end to end, recipes for doing things by hand, and a glossary the AI keeps current.

The workflow

Seven skills, one profile file.

Amber marks where you decide. Everything else runs on its own. Project values (build and test commands, branch, pull-request mode) live in one file, .claude/workflow.conf.

/onboard

Teaches the AI your project once: explores the code, proposes the profile, fills CLAUDE.md, writes a map and glossary, adopts existing features.

Install

Two minutes to the first feature.

  1. Install into any project, new or existing. Existing files are never overwritten. Add --stack dotnet, node, or python for stack-specific extras.

  2. Run /onboard in Claude Code so the AI understands the codebase before it touches it.

  3. Start. /feature for something new, /change for existing code, /status when you come back tomorrow.

Node 18 or newer, git, Claude Code 2.1 or newer. MIT licensed. No telemetry.

Questions

Before you try it

Does it work with my language or framework?

Yes. The core needs a build command, a test command, and git. Stack packs add extras (an EF Core migration skill for .NET, permission presets for Node and Python), and you can write your own.

Will it overwrite my CLAUDE.md or settings?

No. init keeps every existing file, and update only refreshes the skills, the reviewer, and the hook. Your config, rules, feature docs, and handbook are yours.

How much will it ask me?

As little as possible. A question is asked only if the code cannot answer it, a wrong guess would be expensive to undo, and reasonable people would choose differently. Everything else is decided and written down for you to overrule.

Can my team use it with other coding agents?

The state lives in plain files, so any agent that reads markdown can follow it; AGENTS.md points them at the same documents. The skills themselves are written for Claude Code.
