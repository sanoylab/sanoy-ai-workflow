The problem

Vibe coding is fast until you have to change it.

An agent that writes code nobody understands leaves you with a project you cannot change safely. Sanoy keeps the speed and removes the blindness: every feature gets a plan you approve, tests written first, a build that must pass before the agent finishes its turn, a second agent that reviews with fresh eyes, and a living document that records what the feature does now, where its code lives, and every change since.

It came out of a real production codebase (a modular .NET platform with six modules and forty-seven features) and was generalized so it works with any language or framework.

How it works

Two lanes. One home per feature.

Amber boxes are the moments you stay in control. Everything between them runs on its own, with an explicit list of things that make the agent stop and ask (an unplanned migration, shared infrastructure, security behavior, scope growing).

What you get

Guardrails that do not slow you down.

_features/<slug>/feature.md

One living document per feature

What it does now, the code map, design decisions, a walkthrough, and every change with its root cause. Claude resolves "the export button", #1342, or a slug to the right doc.

/onboard

Reads before it asks

Parallel explorers learn an existing codebase, propose the build and test commands, fill CLAUDE.md, write a map and glossary, and adopt your existing features. A blank project gets a short interview and a plan.

verify-build.js

A build gate the agent cannot skip

A Stop hook fingerprints your source changes and rebuilds before Claude ends its turn. On errors it blocks and feeds them back. Node based, so it behaves the same on Windows, macOS, and Linux.

reviewer

Fresh-eyes review

A read-only subagent checks correctness, architecture rules, data access, security, tests, and scope before anything ships, and reports only what it can point to in the code.

auto | pair | coach

Learn while you ship

Let the agent write everything, leave the core pieces for you with tests already in place, or take one step at a time with review. Quiz yourself on any feature.

Feature: <slug>

Git and your tracker remember

Every commit carries a feature trailer and, when known, a work item link. /pbi creates GitHub issues or Azure DevOps items from a feature or a change entry.

Every project-specific value lives in .claude/workflow.conf: build and test commands, default branch, pull-request mode (gh, glab, Azure DevOps link, plain URL), and the work item tracker. Skills read it when invoked; the hook reads it when the agent stops.

Install

Two minutes to the first feature.

  1. Install into any project, new or existing. Existing files are never overwritten. Add --stack dotnet, node, or python for stack-specific skills and permissions.

  2. Run /onboard in Claude Code. It learns the codebase, fills the profile and CLAUDE.md, writes the handbook map, and adopts existing features.

  3. Check the setup from outside with doctor. Later, update refreshes the skills without touching your config.

  4. Start. /feature for something new, /change for existing code, /status when you come back tomorrow.

Requirements: Node 18 or newer, git, Claude Code 2.1 or newer. gh for GitHub pull requests and issues.

terminal
# any stack
$ npx sanoy-ai-workflow init

# with a stack pack: dotnet, node, python
$ npx sanoy-ai-workflow init --stack dotnet

# later
$ npx sanoy-ai-workflow doctor
$ npx sanoy-ai-workflow update
What lands in your repo

Plain files. No lock-in.

Everything is markdown, JSON, and one small Node script. Other coding agents can follow the same state through AGENTS.md. Delete the folder and the workflow is gone; your code and your feature docs stay readable.

Questions

Before you try it

Does it work with my language or framework?

Yes. The core is stack-agnostic: it needs a build command, a test command, and git. Stack packs add conveniences (an EF Core migration skill for .NET, permission presets for Node and Python) and you can write your own in a folder.

Will it overwrite my CLAUDE.md or settings?

No. init keeps every existing file unless you pass --force, and update only refreshes the files the kit owns (skills, the reviewer, the hook). Your config, rules, features, and docs are yours.

How many questions will it ask me?

Few, on purpose. A question is asked only if the code cannot answer it, a wrong guess would be expensive to undo, and reasonable people would choose differently. Everything else is decided and listed as "decisions I made for you", so you overrule by reading, not by answering.

Does it send anything anywhere?

No telemetry, no network calls from the CLI or the hook. The only network use is what you configure: pushing to your remote, creating a pull request, or creating a work item in your own tracker.

What happens if the build breaks?

The Stop hook returns the error lines to Claude and blocks it from finishing until the build is green. If nothing relevant changed since the last green build, it does not build at all.

Can my team use it with other coding agents?

The state lives in files, so any agent that can read markdown can follow it. AGENTS.md points Codex, OpenCode, and Copilot at the same documents. The skills themselves are written for Claude Code.

Why "Sanoy"?

It is the author's first name, Yonas, spelled backwards. The workflow was extracted from his production project and generalized so anyone can use it.
